# Atlas: generate the instance's loop workflow

## Purpose

Turn the instance's topology — who the prototypes are for (ICP), which surfaces
carry experiments, what signal measures them — into a **generated orchestration
workflow** tailored to this repo. The division of labor:

- **This skill** is the interactive front door: it asks the topology questions
  (workflow scripts cannot ask questions mid-run) and persists the answers.
- **The generated workflow** (`.claude/workflows/<slug>-loop.js`) is the
  deterministic multi-agent artifact: it advances every running experiment via
  `systemix loop <id>` (one card-writing code path — close-proposal cards dedupe
  in `.systemix/queue.json`), audits each surface against the ICP, and queues
  ONE synthesis card. It is propose-only and never closes an experiment.
- **Hermes** may later propose diffs to the generated files — like all
  self-modification, those land as HITL queue cards, never direct writes.

## Steps

### Step 0 — Recall context

- Read `systemix.config.yaml`. If it already has an `atlas:` block, this is an
  **update**: use the stored answers as interview defaults and regenerate
  (idempotent — same slug, same file paths, no duplicates).
- Read `experiments/LEARNINGS.md` (recent entries) and list running experiments
  (`systemix experiment list` or MCP `experiment_list`) so interview suggestions
  start from evidence, not a blank slate.
- If no signal source is wired (`signals.*` absent/unconfigured in the config),
  say so and recommend `/connect-signal` first — the generated workflow degrades
  to audit-only without evidence, and the interview should make that explicit.

### Step 1 — Interview the topology

Ask (AskUserQuestion where options are enumerable, free text otherwise). Offer
defaults inferred from the repo (routes under `src/app/`, existing experiments'
`section` + `posthog-event` fields):

1. **ICP** — one sentence: who are the prototypes for?
2. **Surfaces** — which routes/pages carry experiments? For each: a short name,
   the source path, and its primary conversion event.
3. **Cadence** — how should the workflow run: manually (via the runner skill),
   or on the existing daily cron alongside `systemix loop`?
4. **Evidence window + thresholds** — default `--days 30` and the instance's
   `hermes.thresholds`; only override if the user asks.
5. **Audit breadth** — max experiment candidates the ICP audit may propose per
   run (default 3; more is noise, not thoroughness).

Derive `<slug>` from the repo/instance name (kebab-case).

### Step 2 — Stage the three writes (do NOT write yet)

1. **Topology block** — merge into `systemix.config.yaml` (source of truth for
   regeneration; the workflow bakes a copy):

   ```yaml
   atlas:
     icp: "<icp>"
     surfaces:
       - { name: <name>, path: <path>, conversionEvent: <event> }
     evidenceDays: 30
     maxCandidates: 3
   ```

2. **The workflow** — instantiate the bundled `loop.template.js` (next to this
   SKILL.md) into `.claude/workflows/<slug>-loop.js`:
   - replace every `__SLUG__` with the slug;
   - replace the object after `/*__ATLAS_TOPOLOGY__*/` with the interview's
     topology as a JS object literal;
   - leave the rest of the template untouched — orchestration logic changes go
     through the template + regeneration, not per-instance hand-edits.

3. **The runner skill** — `.claude/skills/<slug>-loop/SKILL.md`, the explicit
   opt-in door for multi-agent orchestration:

   ```markdown
   ---
   name: <slug>-loop
   description: Run the generated <slug> validation-loop workflow — advance running experiments to decision-ready, audit surfaces against the ICP, queue one synthesis card. Generated by /atlas; regenerate with /atlas update.
   version: "0.1.0"
   ---

   # Run the <slug> loop workflow

   Invoke the Workflow tool with
   `{ "scriptPath": ".claude/workflows/<slug>-loop.js" }`.

   When it returns, summarize: experiments advanced (and their terminal
   states), audit candidates proposed, and the queue card id. Point the user
   at pending cards: decisions happen there, not here. If the Workflow tool
   is unavailable, run `systemix loop` instead (the single-agent pass) and
   say the audit phase was skipped.
   ```

### Step 3 — HITL gate

The workflow script and the runner skill are **self-modification-class
artifacts** (under write-policy the workflow script is the `workflow` artifact
and the runner skill the `skill` artifact: always proposed, even at
autonomous). Present all three staged writes as one diff and get
explicit approval before writing anything. On approval, write the files and
remind the user to commit them — the instance stays reproducible in CI.

### Step 4 — Wire the cadence

- **Manual**: done — `/  <slug>-loop` runs it.
- **Cron**: append `npx claude -p "/<slug>-loop"` guidance to the instance's
  existing daily loop workflow (or `systemix schedule` if configured). Show the
  change; don't silently edit CI files — that's a fourth HITL write.

### Step 5 — Report

Confirm what was generated and the contract in one line: *"the workflow
advances and proposes; humans close — via `/close-experiment` from the queue
cards."* Suggest a first run.

## Guardrails

- **Never closes, never applies**: the generated workflow only queues cards.
- **Always HITL to (re)generate**: every write this skill makes is proposed
  first, at every autonomy tier.
- **Idempotent**: re-running `/atlas` updates in place (same slug → same
  paths); it must never mint a second workflow for the same instance.
- **One card path**: experiment advancement goes through `systemix loop <id>` —
  do not teach the workflow to write `close-proposal` cards itself.
